**Статус:** резюме фактически проведённого обсуждения (этот чат)
**Не является:** реконструкцией другого разговора, спецификацией к реализации

## 1. Исходная задача и метод

Цель — не спроектировать язык семантического графа теоретически, а
**эмпирически определить минимальный язык**, достаточный для описания
реального программного проекта (биржа), проверяя каждое понятие на
практике, прежде чем вводить его.

Ключевое правило, сформулированное и ни разу не нарушенное осознанно:

> Новое понятие вводится только после того, как реальный граф не смог
> ответить на конкретный вопрос без него.

Процесс:

```
Артефакт → Наблюдение → Попытка выразить существующим языком
    → удалось → следующий факт
    → не удалось → исчерпать альтернативные формулировки
        → всё ещё не удалось → MCR
```

## 2. Базовый язык (v0.1)

```
Frame     — самостоятельная сущность (участвует хотя бы в одной
            независимой семантической связи; иначе — атрибут)
Relation  — типизированная связь между двумя Frame
Fact      — триплет (Frame, Relation, Frame)
```

Критерий «фрейм или атрибут»:

> Фреймом является сущность, способная участвовать хотя бы в одной
> независимой семантической связи. Всё остальное — атрибут.

Подтверждено на артефакте (реальный HTTP/SQL-лог сделки, затем —
документация Taxi API): операционные, безусловные, локальные факты
(`API — creates/updates/reads → BusinessEntity/DatabaseField`)
выражаются языком без семантической натяжки в большинстве случаев.

---

## 3. Дисциплина процесса

| Понятие | Смысл |
|---|---|
| **MCR** (Model Change Record) | Единица истории языка: вопрос → эксперимент → результат → (не)изменение |
| **Гипотеза** | Утверждение с явным статусом: Hypothesis → Supported (со scope) / Rejected |
| **OQ** (Open Question) | Вопрос, для которого пока нет метода проверки (не гипотеза — гипотезу можно проверить существующим методом) |
| **Наблюдение (R-N)** | Слабейший уровень фиксации: просто то, что увидено, без интерпретации |

Правила, подтвердившие себя многократно:

- **Факт ≠ объяснение.** Разложение результата на «что произошло» и
  «почему» — постоянно нарушаемое и постоянно восстанавливаемое
  разделение.
- **Имя появляется последним.** Явление называется только после того,
  как воспроизвелось независимо (не по первому совпадению).
- **Один эксперимент — одна гипотеза.** Смешение вопросов (форма +
  семантика, представление + квантификация) систематически приводило
  к неинтерпретируемым результатам.
- **OQ ≠ гипотеза-кандидат по сходству.** OQ открывается только когда
  попытка проверки уперлась в тупик, а не когда два результата
  показались похожими.

## 4. Основные завершённые исследования

### MCR-001 — граница системы и первый факт сценария
Первая попытка (`User — initiates → Screen`) провалилась сразу по двум
пунктам словаря (тип и связь). После исчерпания альтернатив
(`Role`, `UseCase`, `displays`, `contains`) выяснилось: проблема не в
отсутствии слов, а в **семантической перегрузке** существующих связей
(`uses` означает одновременно «программная зависимость» и
«пользовательское взаимодействие»).

→ Открыло **H-D**: нужен ли Actor/Role как Frame на границе системы.

### MCR-002 — конструкция «доступно только X»
Три независимые ветки представления (`Role → API`, `Role ↔ Permission`,
`API → Role`) не смогли выразить исключительность правила доступа без
потери смысла. Лучший кандидат — `validates`, но и он не кодирует
«только», а не «в том числе».

→ Частично сузило H-D (не про существование Role вообще, а про
выразимость quantified access rules).
→ Гипотезы: H-MCR002-A (проблема исключительности), -B (проблема
модели прав), -C (проблема самой формы бинарных отношений — по форме
похожа на OQ-001, связь не исследовалась).

### E-3A / E-3B / OQ-001 — причинность между фактами
Простое правило (`u_phone → сброс u_phone_checked`) удалось разложить
на два операционных факта, но не удалось связать их причинно —
ни одна Relation в словаре не описывает связь между **фактами**
(не между фреймами). Конструкция reification (`Fact` как объект
`caused_by`) прошла только этот простой случай.

→ **OQ-001**: может ли Fact быть полноценным объектом Relation, или
это работает только как нотация для простой парной причинности?
Воспроизведено на независимом правиле (N-007, множество) — подтверждён
как повторяющийся, но не решённый вопрос.

### R-2 / N-007 — правила над множеством
`Booking` завершается, если **все** связанные `DriverCandidacy` имеют
состояние 6. Разложение на факты не снимает проблему: квантор по
переменному множеству — отдельная, не решённая форма выразимости,
не сводится к правилу 1 (проверено явным экспериментом: попытка
привести правило 2 к форме правила 3 не удалась).

### H-ENG-001 / H-ENG-002 — инженерные гипотезы
- **H-ENG-001** (reification): проходит только простейший случай, не
  решает ни множества, ни условия. Зафиксирована как частично
  подтверждённая, не как принятое решение.
- **H-ENG-002** (`LogicNode`): не решение, а «карта незавершённости» —
  свела 4 открытых вопроса к двум уже известным (H-D, OQ-001) и двум
  новым (язык выражений внутри условия; природа LogicNode как типа).

### R-6 / R-7 / OQ-002 — литералы и значения
Попытка выразить конкретное значение (`rate = 2`) двумя независимыми
путями:
- через **событие** (`API updates BusinessEntity`) — нет слота для
  значения у Relation → **R-6**
- через **состояние** (`BusinessEntity has_state State(...)`) — `State`
  до сих пор использовался только для категориальных значений из
  конечного перечня, не для чисел из диапазона → **R-7**

→ **OQ-002**: независимы ли R-6 и R-7 или общая причина? Не
исследовано намеренно (различие с H-MCR002-C зафиксировано как
«замечание о сходстве», не как OQ — по критерию «OQ появляется только
при упоре в тупик, не при внешнем сходстве»).

## 6. Калибровка измерительного инструмента (Цикл 3)

Отдельно от языка была выработана и **откалибрована** дисциплина
оценки кандидатов на реальном корпусе (9 независимых артефактов:
Terraform, SQL DDL, React, Playwright, GitHub Actions, OpenAPI, BPMN,
Docker Compose, Markdown ADR):

```
✔  Accepted           — совпадает с уже проверенным употреблением
⚠  Review              — граф строится, подозрение на расширение смысла
✖F Reject-Frame        — не найден подходящий тип
✖R Reject-Relation     — не найдена подходящая связь
   + бит уверенности (?) — было ли решение очевидным
```

Результат калибровки: шкала не менялась 9 циклов подряд (стабильна),
скорость разбора не деградировала (воспроизводима). **Calibration v1.0
заморожена.**

Наблюдения по корпусу (не проанализированы, только зафиксированы):
- Reject-Frame систематически группируется вокруг «внешних по
  отношению к системе» объектов (образы, шаги пайплайна, решения).
- Reject-Relation систематически группируется вокруг
  ветвления/условных исходов — пересекается с R-2/OQ-002.

## 7. Архитектура инструмента (Semantic Graph Builder)

Итоговая, замороженная перед реализацией модель:

**Контур исполнения (детерминированный, без обучения и эвристик):**
```
Repository → Parser → Candidate Builder → Classifier (Registry vN)
    → Node + Edge → Graph vN
```

**Контур накопления (append-only, неизменяемые сущности):**
```
Build, Candidate, Classification, Node, Edge, Registry, MCR
```

**Контур исследования (вычисляемый, не хранимый):**
```
Corpus → Analytics View (произвольные проекции: by Relation,
    by ObjectType, by Relation+Object, growth over builds, ...)
    → MCR Candidate → Human Review → Registry vN+1
```

Ключевые решения:
- `Candidate` — гипотеза («мне кажется, здесь есть кандидат»), не
  утверждение; существует только внутри одного `Build`
  (`candidate_id = build_id + ordinal`, идентичности между сборками нет).
- `Classification` несёт статус (`ClassificationStatus`, не
  `EdgeStatus`) и обоснование; сверяется с `Registry` конкретной версии.
- `Edge`/`Node` создаются только из `ACCEPTED` — уже не несут
  сомнения, это факт графа.
- `Registry` меняется **только** через MCR — не руками, не
  автоматическим обучением.
- **Research Queue не хранится** — это семейство вычисляемых
  представлений (`Pattern` — описание, `PatternKey` — определяется
  агрегатором, а не Candidate) над неизменяемым корпусом наблюдений.
- **Builder никогда не обучается.** REVIEW — это не обучающий сигнал,
  а осознанный отказ от автоматического решения. Единственный путь
  изменения языка — явный MCR.
- Полная пересборка графа при повышении версии Registry — не патчи.
- Всё append-only: ничего не редактируется постфактум, только
  создаются новые версии.

## 8. Статус на момент паузы

Язык и архитектура инструмента спроектированы до той точки, где
дальнейшее уточнение продуктивнее вести на реализации и на реальном
прогоне (`sgb build`), а не на схемах. Три содержательных открытых
вопроса (H-D, OQ-001, OQ-002) и одна незавершённая ветка (R-2) остаются
явно зафиксированными как нерешённые — это рабочая, а не финальная
карта языка.

Сама архитектура Builder тоже не аксиома: как и любая другая
конструкция в этом исследовании, она подлежит проверке на первом
реальном прогоне и может потребовать пересмотра тем же способом,
каким пересматривались решения о языке.
